# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Two independent npm packages, no workspace/monorepo tooling. Install and run each separately.

- `backend/` — Express 5 + TypeScript (ESM, `"type": "module"`) + Prisma 7 / PostgreSQL
- `client/` — React 18 + TypeScript + Vite + Redux Toolkit Query + SCSS

## Commands

Backend (`cd backend`):
- `npm run dev` — dev server via `tsx watch ./src/app.ts` (`PORT` from the environment, default 3000; read after `config()` so a `.env` value is honoured and the real env wins under Docker)
- `npm run build` — `prisma generate && tsc` → `dist/`, then copies the generated client to `dist/generated/`. That copy step is required: the client is emitted as `.js` under `src/generated/` and `tsc` will not carry it across, so `npm start` fails without it.
- `npm start` — `node dist/app.js` (requires a build first)
- `npm run migrate:dev` — create + apply a migration from schema changes
- `npm run migrate:deploy` — apply pending migrations (production/CI)
- `npm run studio` — Prisma Studio data browser
- `npm run grant:root -- <firebase-uid>` — makes that account the store owner. The only way to create the *first* owner, and the recovery path if ownership is stranded; see the access-control notes below for why it is not an endpoint. In a container it is `node dist/scripts/grant-root.js <uid>` — the source lives in `src/scripts/` precisely so `tsc` compiles it into `dist/`, since the runner image installs `--omit=dev` and has no TypeScript runtime to launch a `scripts/*.ts` file with.

Postgres runs as the `db` service in `docker-compose.yml`; `docker compose up -d db` starts it.

## Containers

**nginx compresses what it proxies, and that needs saying out loud.** `gzip_proxied any` is set in both server blocks. Its default is `off`, which disables compression for *every* proxied response — so the JS bundle was gzipped and all the JSON behind `/api` was not, which on a catalogue or order page is the larger payload of the two. `gzip_vary on` goes with it, because those URLs now serve different bytes depending on `Accept-Encoding`.

`/uploads` is served `Cache-Control: public, max-age=1y, immutable`, set in `app.ts`'s `express.static` rather than in nginx so a deploy that exposes the backend directly gets it too. That is safe precisely because multer names files from a UUID and never reuses one: editing a product's photo writes a *new* file and repoints the row, so the bytes at a given `/uploads` URL genuinely never change. Without it every product card on every page cost a revalidation round trip to be told "unchanged".

**Both sites carry a Content-Security-Policy, and they are different policies.** The console has had one since it was built; the storefront went without, which was the wrong way round — the shop is the side that renders product copy, review text and customer names, so it is the side an injection lands on. Each `server` block holds its policy in a `set $csp` variable, because `add_header` is not inherited by a location that sets headers of its own and the policy therefore has to be repeated verbatim in the `= /index.html` / `= /admin.html` block; the console previously kept two hand-maintained copies, which is how an edit ends up applying a different policy to the entry document than to everything else.

The storefront's policy is the looser of the two only because it has to be: `checkout.razorpay.com` (the payment modal, plus `api.` and `lumberjack.` for the calls it makes once open), the Google/gstatic origins Firebase auth and the invisible reCAPTCHA need, and googletagmanager/google-analytics for Firebase Analytics. The console lists none of those — no Razorpay because an operator never pays for anything, and no analytics because `src/admin/firebase.ts` omits it deliberately. `connect-src 'self'` assumes the API is same-origin, which it is behind this nginx; a deploy pointing `VITE_SERVER` at a separate backend host must add that origin or every request is blocked, and that is the one edit this policy is likely to need.

**Liveness and readiness are separate endpoints** (`backend/src/app.ts`), because a caller that conflates them makes the wrong decision. `GET /health` touches nothing external and so stays 200 through a database outage — an orchestrator that restarts on this signal must not kill the API because Postgres is briefly away, since that changes nothing about the database and discards every in-flight request too. `GET /health/ready` runs `SELECT 1` and answers 503 when the pool does not. Prisma connects lazily, so a backend that cannot reach Postgres at all will listen happily and fail on the first customer to load the catalogue; readiness is what catches that. Compose's `backend` healthcheck probes `/health/ready`, since `web` waits on `service_healthy` before nginx sends anyone to it. Failing it does not restart the container — Compose does not restart on healthcheck failure, only Swarm does — so a blip marks the container unhealthy and nothing more, which is the wanted behaviour. Both live outside `/api/v1` deliberately: `routeAudit` would otherwise demand a guard, and a probe needing a credential reports a misconfigured credential as a dead application. Neither discloses more than up/not-up; the readiness failure is logged server-side because the error text can carry the connection string's host and user.

Access logging is `combined` under `NODE_ENV=production` and `dev` otherwise. `dev` is ANSI-coloured and carries no timestamp or response size, which is unreadable in anything aggregating logs after the fact. Both probes are skipped by `morgan` — Compose polls readiness every 30s forever, and on a quiet store that is the majority of the log.

`docker compose up -d` brings up the whole stack: `db` (postgres 16) → `migrate` → `backend` → `web` (nginx serving the SPA and proxying `/api` + `/uploads`). The `migrate` service reuses the backend image, runs `prisma migrate deploy`, and exits; `backend` waits on `service_completed_successfully`, so a fresh volume gets its schema before the API starts rather than crash-looping on missing tables.

**Production is the base file plus `docker-compose.prod.yml`**, always both — `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d`. The runbook is `docs/deployment.md`. An overlay rather than a forked compose file, because a fork has to be kept in step by hand and the copy that drifts is always the production one, discovered during an incident. It adds Caddy (TLS, auto-renewing certs — no certbot timer to notice has stopped running), a `pg_dump` backup service, and bounded container logs; and it closes the ports the base file publishes for convenience.

**`ports: !override` in that overlay is load-bearing.** Compose merges list fields by *appending*, so without the tag the overlay's binding is added to the base file's rather than replacing it: Postgres stays listening on all interfaces while the file appears to have closed it, and nginx keeps claiming port 80, which collides with Caddy so the stack will not start at all. Verified both ways. Anything else that narrows a base-file list needs the same tag.

**`TRUST_PROXY` must equal the number of proxies in front of the backend, exactly** — 1 for the base stack (nginx → backend), 2 under the overlay (caddy → nginx → backend), 3 behind Cloudflare or a cloud load balancer. Each layer appends to `X-Forwarded-For`. Too low and `req.ip` resolves to the nearest proxy, putting every visitor in one rate-limit bucket — and `globalLimiter` is app-wide, so the first person to trip it locks out the whole store. Too high and the client can forge the address the limiter keys on. Neither failure produces an error, which is why it is an env var read in `app.ts` rather than a literal: it is a property of the deployment, not of the code.

HSTS is set by Caddy, not by nginx, because nginx also serves the plain-HTTP local stack — sending HSTS from there teaches a browser to force HTTPS against a development stack that has none, curable only by clearing the browser's HSTS store by hand. It deliberately omits `preload`, which is a one-way door baked into browser binaries.

Node base images are `node:24-alpine` (Active LTS). Postgres is pinned to 16 deliberately — bumping the major would require `pg_upgrade` against the existing `pgdata` volume, not just a tag change.

`VITE_*` values are baked into the client bundle at **image build time**, so changing any of them needs `docker compose build web`, not just a restart.

**Two sites come out of the one `web` image.** `client/nginx.conf` has two `server` blocks: `app.admin.<domain>` (regex `~^app\.admin\..+$`) serves `admin.html`, everything else serves `index.html`. Each block explicitly 404s the *other* entry document, so the console's bundle is never served from the shop's origin and vice versa. Both blocks proxy `/api` and `/uploads` to the same backend, which is what keeps each SPA same-origin with the API. Point an `app.admin.<domain>` DNS record at the same server and add it to Firebase's authorized domains, or Google sign-in on the console fails with `auth/unauthorized-domain`.

Client (`cd client`):
- `npm run dev` — Vite dev server
- `npm run build` — `tsc && vite build`
- `npm run lint` — `eslint .` (flat config in `eslint.config.js`; ESLint 10 no longer reads `.eslintrc`)

`npm run build` builds **two entries** (`vite.config.ts` → `rollupOptions.input`): the storefront (`index.html` → `src/main.tsx`) and the admin console (`admin.html` → `src/admin/main.tsx`).

**The console is only ever reachable by hostname, never by path — in dev as well as in production.** One Vite server serves both entries, so a dev-only middleware in `vite.config.ts` picks the entry document from the `Host` header exactly as the two nginx `server` blocks do, and each host 404s the other's entry document (`/admin.html` on the storefront, `/index.html` on the console). Browsers resolve any `*.localhost` name to loopback with no hosts entry, so `npm run dev` gives you:

- storefront — http://localhost:5173
- console — http://app.admin.localhost:5173

There is deliberately no path-based way in. A `/console`-style route would be a URL that works on a developer's machine and 404s on the server, and it would be a second door to keep locked. Because the console is at the root of its own host in both environments, its router needs no basename.

Both packages: `npm test` (`vitest run`) and `npm run test:watch`.

**The tests are unit tests over pure functions, and that scope is deliberate.** `backend/src/utils/__tests__/` covers the pricing and refund arithmetic, the coupon rules, the unsubscribe HMAC and the variant form parser; `client/src/**/__tests__/` covers the cart's totals and the variant matcher. None of them touches Postgres or the DOM, so `npm test` needs no database and no jsdom, and CI runs both without a service container.

What that leaves uncovered is stated rather than hidden: the controllers, the auth guards and the route audit have no tests. What is covered is the arithmetic that decides money and the parsing that decides what reaches the database — the two places where an error is silent and expensive. Adding a controller test means adding a database to CI, which is a real decision and not a drive-by.

The cart's totals are tested on **both** sides on purpose. They are computed twice — in `cartReducer.calculatePrice` for the preview and in `calculateOrderAmounts` for the charge — and a divergence between them shows a customer one number and bills another.

`.github/workflows/ci.yml` runs both packages on push and PR: typecheck, test and build for the backend (with `prisma generate` first, since the client is no longer committed), and lint, test and build for the client. Node 24, matching the `node:24-alpine` image — a CI that builds on a different major can pass while the image fails.

## Environment

`backend/.env`: `DATABASE_URL`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `CLOUD_NAME`, `CLOUD_API_KEY`, `CLOUD_API_SECRET`, `RESEND_API_KEY`/`MAIL_FROM`/`STORE_NAME` (order email; all three optional — unset logs instead of sending), `MAIL_UNSUBSCRIBE_SECRET` (optional; falls back to `RAZORPAY_KEY_SECRET`, namespaced so the two signatures are never interchangeable), `CLIENT_URL` (comma-separated allowed CORS origins) and `ADMIN_URL` (the console's origin — allowed for CORS *and* pinned on every admin route, see below). The pin reads `ADMIN_URL` **lazily, on first request**, not at import: ESM evaluates every import before `app.ts` reaches its own `config()`, so a module-level read saw `undefined` and turned the pin off for any `.env`-based deploy while appearing to work under compose. A control whose failure mode is "silently off" has to be evaluated late. With `NODE_ENV=production` and no `CLIENT_URL`, cross-origin requests are refused rather than allowed — behind the compose nginx the SPA is same-origin, so that default is correct there.
Root `.env` (docker compose only): the above plus `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB`/`POSTGRES_PORT` and the `VITE_*` client build args. Inside compose the DB host is the service name `db`; from the host it is `localhost:${POSTGRES_PORT}`.

`client/.env`: `VITE_SERVER` (storefront's backend origin, no trailing slash), `VITE_FIREBASE_*` (key, domain, project id, bucket, sender id, appid, measurement id), `VITE_ADMIN_SERVER` (the console's API origin — empty in production, since nginx proxies `/api` on the console's host; set to the backend for `npm run dev`). The storefront is deliberately **not** told where the console lives — it links to it from nowhere, whatever role the signed-in account holds, so an operator browsing the shop is just a customer there and reaches the console by its own URL. `VITE_STORE_NAME`/`VITE_SUPPORT_EMAIL`/`VITE_SUPPORT_PHONE`/`VITE_STORE_ADDRESS` are the store's identity as the policy pages render it, and `VITE_SITE_URL` is the canonical origin for `<link rel="canonical">` and the `og:` tags. `VITE_SOCIAL_FACEBOOK`/`_TWITTER`/`_INSTAGRAM`/`_PINTEREST` are the footer's social links, and unlike every value above them they have **no defaults** — the footer renders an icon only for a profile whose URL is set, and only for an `http(s)` one. They replaced four `href="#"` anchors: a click that scrolls to the top and does nothing reads as a broken site, where a missing icon reads as a shop that is not on Pinterest. All of them are declared in `src/vite-env.d.ts`, so a typo is a compile error rather than `undefined` at runtime.

**A `VITE_*` that is not also a build arg does nothing under compose.** The store-identity values were in `.env.example` for months while `client/Dockerfile` and `docker-compose.yml` never passed them, so every containerised deploy rendered `[set VITE_STORE_ADDRESS]` in its own returns policy however the root `.env` was filled in — the placeholders did their job and pointed at the wrong cause. Adding a `VITE_*` means adding it in **four** places: `vite-env.d.ts`, `.env.example`, the Dockerfile's `ARG`/`ENV` pair, and the compose `build.args`.

The pricing values (`TAX_RATE`, `SHIPPING_FEE`, `FREE_SHIPPING_THRESHOLD`, `SHIPPING_ZONES`, `COD_*`, `RETURN_WINDOW_DAYS`, `LOW_STOCK_THRESHOLD`) are **backend** variables, not `VITE_*`, deliberately: the client fetches them at runtime from `GET /api/v1/config/storefront`, so changing a tax rate is a backend restart rather than a rebuild of two applications.

`VITE_SERVER` is deliberately **not** read by the console — pointing it at the storefront's origin would make every admin request cross-origin, which is exactly what the origin pin refuses.

## Backend architecture

**ESM import rule** — `module: "NodeNext"` with ESM output means every relative import must carry a `.js` extension even in `.ts` source (`import { prisma } from "../utils/db.js"`). Omitting it breaks at runtime, not compile time.

**Database access** — a single `PrismaClient` (`prisma`, exported from `src/utils/db.ts`) backed by the `@prisma/adapter-pg` driver adapter. Schema lives in `prisma/schema.prisma`; Prisma 7 keeps the connection URL in `prisma.config.ts` (CLI) and the adapter (runtime), *not* in a `url` field on the datasource. `src/utils/db.ts` imports `dotenv/config` itself because ESM evaluates it before `app.ts`'s own `config()` call.

**Money is `Decimal`, not float.** Every price/total column is `@db.Decimal(10,2)`, so Prisma hands back `Decimal` objects that serialize as `{"s":..,"e":..,"d":[..]}` if passed straight to `res.json()`. Convert at the boundary via `src/utils/serialize.ts`.

**Response shaping** — the client still reads Mongo-era shapes (`_id`, a nested `shippingInfo`, `orderItems`). `src/utils/serialize.ts` rebuilds them from the relational rows, which is why the frontend needed no changes. It is the single place to touch if the client ever moves to plain `id`.

**Catalogue search is trigram-indexed, on the raw columns.** The indexes are `GIN (name gin_trgm_ops)` / `GIN (brand gin_trgm_ops)` — *not* over `lower(...)`, which is what `add_search_trigram_indexes` originally created and what `realign_search_trigram_indexes` replaced. The original was written for `getAllProducts`, and its own comment said so, but `getAllProducts` filters with Prisma's `mode: "insensitive"`, which emits `ILIKE`; the planner will only use an expression index when the predicate matches the expression *exactly*, so `ILIKE` could never use a `lower(name)` index. The endpoint the indexes existed for sequentially scanned Product on every search while the type-ahead over the same column used one. Nothing looked broken because both returned the right rows — measured at 60k rows, a selective term went 28.9 ms → 0.5 ms once the index actually applied.

pg_trgm answers `LIKE`, `ILIKE` and the regex operators from a raw-column `gin_trgm_ops` index, so one pair of indexes serves both callers and `suggestProducts` uses `ILIKE` too. If you add a third search predicate, make it `ILIKE` on the bare column as well — a fourth trigram index is real write amplification, and an expression index that does not match its predicate is worse than none, because it looks like coverage.

**Catalogue search is trigram-indexed.** `getAllProducts` and `suggestProducts` both match with an infix `ILIKE '%term%'`, which a btree index cannot answer — a leading wildcard means a sequential scan. The `add_search_trigram_indexes` migration installs `pg_trgm` and adds GIN indexes over `lower(name)` and `lower(brand)`. The `lower()` in those index expressions has to match the predicate exactly or the planner ignores them, which is why `suggestProducts` lowercases both sides itself instead of using Prisma's `mode: "insensitive"`. Prisma cannot express an expression index with an operator class, so the two GIN indexes exist in SQL only and will never appear in `schema.prisma`; `prisma migrate diff` will not miss them, but a hand-written schema reset would.

`suggestProducts` is raw SQL (`$queryRaw`, tagged-template form so the term is bound, not interpolated) because it needs `similarity()` for ranking. Terms are run through an escape for `%`, `_` and `\` before going into the pattern — otherwise a search for `%` matches the entire catalogue. It deliberately does **not** call `reviewStatsFor`; that is a second grouped query over Review to draw stars a dropdown does not render.

**"You may also like" is ranked in SQL, not filtered in the client.** `GET /product/:id/related` scores candidates — 3 for same category *and* brand, 2 for same category, 1 for same brand — then orders by review count and recency, `LIMIT 10`. Both legs are indexed (`Product_category_idx`, `Product_brand_idx`). It tops up with recent arrivals only when the related set is short, so a product alone in its category still gets a rail, but filler never outranks a real match.

Two traps it exists to avoid. `brand` defaults to `""` and most rows still have it empty, so an unguarded `brand = $brand` makes every brandless product related to every other one — the query only matches on brand when the current product actually has one. And the rail it replaced was `getlatestProducts` filtered client-side with `.filter(i => i._id !== product._id)`, which meant the section rendered four cards instead of five whenever the product being viewed was itself among the newest; exclusion belongs in the query that applies the `LIMIT`.

`related-${id}` is cached, but the key that has to be dropped on a product mutation is never `related-${productId}` — adding or editing one product changes the rail of every *other* product in its category or brand. `invalidateCache({ product: true })` therefore drops every `related-` key by prefix, the same reasoning as the suggestion cache's `flushAll`.

**Invariants live in the schema.** `CHECK` constraints enforce non-negative stock/price/total and positive quantity (`prisma/migrations/*_add_check_constraints`). `OrderItem.productId` is `onDelete: Restrict`, so a product with order history cannot be deleted; `WishlistItem` has a composite `@@id([userId, productId])` making duplicate wishlist rows impossible. Coupon limits are likewise CHECKed (`coupon_max_redemptions_positive`, `coupon_per_user_limit_positive`, `coupon_min_order_value_non_negative`) — a limit of zero is refused because it makes a code that can never be redeemed while still reporting as active; `isActive = false` is how a code is turned off. Prefer adding a constraint over adding a runtime check.

**Checkout is order-first, and that ordering is the whole design.** `createCheckout` (`POST /api/v1/order/checkout`) wraps pricing, stock reservation and order creation in one `prisma.$transaction`, writes the order as `PendingPayment` with `stockReserved = true`, and only *then* opens a Razorpay order. Payment is never a precondition for the order existing. Stock is reserved with `updateMany({ where: { id, stock: { gte: qty } }, data: { stock: { decrement: qty } } })` — the check and the decrement are a single atomic statement, so concurrent checkouts for the last unit cannot both succeed.

The previous flow charged the card first and had the browser create the order afterwards; a closed tab meant a charged customer with no order, and stock was only held after the money moved. Do not reintroduce any path that takes payment before an order row exists.

**Payment lives in `utils/orderPayment.ts`, not in a controller.** `markOrderPaid` (PendingPayment → Processing/Paid) and `releaseOrder` (→ Cancelled, stock restored) are the only two transitions, and both are idempotent and keyed on state rather than on caller — three things race for them: `POST /payement/verify` (the browser's report, a fast path), `POST /payement/webhook` (Razorpay's, the authority), and the expiry sweep. `stockReserved` is the flag that makes a double restore impossible; it is read and cleared inside the same transaction as the increment.

**Two payment secrets, two different signatures.** The checkout callback is HMAC'd with `RAZORPAY_KEY_SECRET` over `<order_id>|<payment_id>`; the webhook is HMAC'd with `RAZORPAY_WEBHOOK_SECRET` over the **raw request body**. `app.ts` mounts `express.raw()` on `/api/v1/payement/webhook` *before* `express.json()` for exactly this reason — parsing and re-serializing changes the bytes and the digest stops matching. Both comparisons go through `crypto.timingSafeEqual` in `utils/razorpay.ts`. The webhook answers 200 for handled *and* ignored events, because anything else makes Razorpay redeliver.

**A `PendingPayment` order is holding stock**, so `utils/expireOrders.ts` runs every 5 minutes and cancels anything past `paymentExpiresAt` (30 minutes), restoring its units. It is started from `app.ts`. Anything that ends an order's life must restore stock — `deleteOrder` used to drop the row and leak the inventory permanently.

**Transactional email is fire-and-forget, and hangs off the state machine rather than beside it.** `utils/mailer.ts` is the Resend transport; `utils/emails.ts` holds the templates and the three senders. Every send swallows its own errors like `recordAudit`, for a sharper version of the same reason: the things that trigger mail here have already committed, so a customer whose money has moved must never see a 500 because a mail API was slow, and an order must never fail to ship because the shipping notice did not go out.

**Exactly-once came free from the existing transitions and needed no flag.** The receipt fires inside `markOrderPaid` guarded by `outcome === "paid"` — all three racing callers converge there and only the one that actually moved the row gets that outcome. The cancellation notice is guarded by `released` in `releaseOrder`, the same boolean that stops the stock being restored twice. The fulfilment notices sit behind `processOrder`'s status guards, so an operator double-clicking gets a 409 rather than a second email. Do not add an `emailSent` column; the row's state already answers it.

`RESEND_API_KEY`/`MAIL_FROM` unset means nothing is sent and each message is logged instead — the store still takes orders. That is logged as an *error* under `NODE_ENV=production` and as an ordinary line otherwise, because "the receipts silently stopped" is not something anyone notices on their own. Both are read lazily inside the functions, never at module scope, for the `ADMIN_URL` reason: ESM evaluates imports before `app.ts` calls `config()`, so a module-level read disables the feature on exactly the `.env`-based deploys that configured it.

**`User.email` is nullable**, because a phone sign-in never provides one. "Nobody to write to" is therefore a routine outcome, not an error: `loadOrderForMail` returns null and the sender skips silently. Anything new that mails a customer has to handle that case rather than assume an address. Product names and addresses are interpolated into HTML that renders in webmail, so everything user-controlled goes through `esc()`.

**Notification mail is a separate category from transactional mail, and the split is enforced in code.** Back-in-stock alerts, review requests and abandoned-checkout nudges all check `User.emailOptOut` through `mayNotify` in `utils/emails.ts` and all carry an unsubscribe link; receipts, delivery notices and cancellations check neither, because opting out of marketing must never suppress the record of what someone paid. A new sender belongs in one group or the other, deliberately — the gate is one function and skipping it is sending marketing without consent.

`GET /api/v1/user/unsubscribe` is the second deliberately-unauthenticated route in the app, and is listed in `routeAudit`'s `PUBLIC` map with its reasoning. The caller is a mail client following a link and has no session; authority is an HMAC over the uid (`utils/unsubscribe.ts`), the same trade the Razorpay webhook makes. Demanding a sign-in there is what makes people press "spam" instead, which costs delivery of the receipts too. The token grants exactly one capability and never expires — a message sits in a mailbox for years, and a stale unsubscribe link is a broken one. The endpoint answers identically for a bad token so it cannot be used to probe for accounts.

**The three notification sweeps live in `utils/notifications.ts`, on their own 5-minute interval next to the expiry sweep.** They are sweeps rather than hooks because the conditions are queries, not events: stock rises in at least three places (an operator edit, a cancellation, the expiry sweep restoring a reservation), and a hook would have to be added to each one correctly, forever. Asking "has stock and somebody is waiting" periodically catches every path including ones added later.

**Every sweep marks before it sends**, and that order is deliberate: a crash between the two loses a message, where the reverse would re-send one. For notifications that is the right way round — a missed restock alert is a disappointment, a duplicate is the store looking broken. The flags are `StockAlert.notifiedAt`, `Order.reviewRequestedAt` and `Order.recoveryEmailSentAt`; there is no scheduler and no queue.

`Order.deliveredAt` exists because `status` records that a parcel arrived but not when, and the review request is scheduled off "a few days after delivery". Orders delivered before that column existed keep NULL and are deliberately **never** asked — backfilling from `updatedAt` would date a year-old delivery to the migration and mail the entire back catalogue at once.

The recovery nudge is **not** the same message as the "order not completed" notice `releaseOrder` already sends. That one is immediate and transactional; this is a nudge a day later and is marketing. It only goes to orders cancelled *for non-payment* (a deliberate cancellation does not want chasing) and only to customers who have not bought anything since — and an order that fails that last test is still marked, or the sweep re-evaluates it every cycle forever.

**Tax and shipping live in `utils/pricing.ts`, and there is one copy of them.** They used to be three literals — `0.18`, `200`, `1000` — in the client's `cartReducer` and again in `calculateOrderAmounts`, with a comment on the server one asking the next person to keep them matching. That is the arrangement that shows a customer one total in the cart and charges another at checkout, and no test catches it because both numbers are individually correct. The server owns them now (`TAX_RATE`, `SHIPPING_FEE`, `FREE_SHIPPING_THRESHOLD`, `SHIPPING_ZONES`, plus the COD and return-window values), the storefront reads them from `GET /api/v1/config/storefront`, and every default reproduces the old number exactly — an unconfigured deploy charges precisely what it charged before.

Every value is read **lazily inside the accessor**, never at module scope, for the `ADMIN_URL` reason: ESM evaluates imports before `app.ts` calls `config()`, so a module-level read sees `undefined` on any `.env`-based deploy and the setting reverts to the default on exactly the deploys that changed it.

The free-shipping threshold beats a per-state zone override, deliberately. A customer told "free over ₹1,000" and then charged ₹150 because of where they live has been lied to, and the payment screen is the most expensive place to put a surprise.

**Variants are a rollup, and that is what makes them cheap.** `ProductOption` holds the axes and their values; `ProductVariant.optionValues` is a `String[]` aligned **by index** to those options in `position` order. Index alignment is only safe because `replaceVariants` (`utils/variants.ts`) is the sole writer and always rewrites both together in one transaction — no endpoint can edit one without the other.

The other half is that `Product.price` stays populated with the *cheapest* variant and `Product.stock` with the *sum*. Every list endpoint, the search, the price filter and every analytics aggregation read those two columns, and **none of them had to learn what a variant is**. `syncVariantRollup` is the only writer of the derived case and runs at the end of `replaceVariants`; anything that changes variant stock must go through it or the rollup silently drifts, and the first symptom is overselling. `reduceStock`/`restoreStock` therefore move the variant *and* the product column by the same amount in the same transaction rather than recomputing.

`replaceVariants` matches existing rows to submitted ones by their option-value **signature**, not by id, so editing a price updates the row in place — necessary because `OrderItem.variantId` is `onDelete: Restrict` and delete-and-recreate would fail on any product that has ever sold. A combination that has been ordered and is missing from the submission is refused by name; setting its stock to 0 is how one is retired.

`resolveVariant` is what checkout uses to decide what is actually being bought. It refuses a bare productId for a product with options (there is no single price to charge or pool to reserve from — it would charge the rollup minimum for whichever combination the customer thought they were buying) and refuses a variantId belonging to a *different* product, which is how a client bug becomes buying a laptop at a T-shirt's price. It is a pure function over the product's own joined variants, so it is unit-tested.

List endpoints send `hasVariants` but not the variants themselves, from one grouped query (`productsWithVariants`, same shape as `reviewStatsFor`). A card needs the boolean because a product with options cannot be added to a cart without one — its button becomes a link to the picker rather than a line checkout would refuse. Only `GET /product/:id` sends the combinations, the same rule the gallery follows.

**Cash on delivery skips `PendingPayment` entirely.** That state exists to hold stock while a customer is away at a payment page; a COD order has nowhere to go, so it is a real order the moment it is placed and starts at `Processing`. It carries **no `paymentExpiresAt`** — enforced by the `cod_order_has_no_payment_expiry` CHECK, not just by the controller, because the failure mode is the expiry sweep silently cancelling good orders half an hour after they are placed and nobody noticing until a customer asks where their parcel went. `GET /order/:id/payment` refuses a COD order outright; without that it would helpfully *create* a Razorpay order for one. Delivery is the payment event: `processOrder` marks a COD order `Paid` on the transition to `Delivered`, guarded on both the method and the current status so a prepaid order settled long ago by the webhook is never touched. `sendOrderPlacedByCod` is the receipt, sent from `createCheckout`, because `markOrderPaid` — which sends the prepaid one — never runs for COD.

**Shipment tracking is captured on the transition that sends the email.** `Order.carrier`/`trackingNumber`/`trackingUrl`/`shippedAt` are written by `processOrder` on the `Processing → Shipped` step, all optional. There is deliberately no separate "add tracking" endpoint: a second screen to remember is a screen that gets skipped, and tracking added afterwards would arrive in no message at all. `trackingUrl` goes through `requireHttpUrl` because it is rendered as an `href` in webmail and on the order page. The URL is stored rather than built from a carrier lookup table — every carrier's URL shape changes on its own schedule and a table of them here would be wrong within a year, and wrong silently.

**Returns are a state machine with money at one specific point.** `Requested → Approved → Received → Refunded`, with `Rejected` and `Cancelled` as exits. Each transition is its own endpoint under `/api/v1/returns` and each checks the *current status* rather than trusting the caller to call them in order — the same discipline `utils/orderPayment.ts` applies to payment, so an operator with two tabs open gets one action and one 409.

Money moves at **`Received`, not at `Approved`**: approving is a promise, the refund is a payment, and in a real warehouse they are days apart. Splitting them also means a Razorpay outage cannot stop an operator recording that the goods are back on the shelf — otherwise they restock by hand, twice.

Scoped to specific `OrderItem`s and quantities rather than to a whole order, because "one of the three shirts didn't fit" is the ordinary case. The allowance is what was ordered *minus* what earlier requests already claimed, counted over requests that were not rejected or withdrawn — a rejected request consumed nothing and must not permanently reduce what someone may return because they once asked and were told no.

`utils/returns.ts` holds the rules and the arithmetic, free of Prisma so both are unit-tested. `refundAmountFor` makes two decisions worth stating, because both are the kind that get quietly reversed: **tax comes back proportionally** (returning a third of the goods returns a third of the tax; refunding the bare item price short-changes the customer by the tax rate on every return), and **delivery comes back only on a full return** (a customer keeping one of three items has still had the parcel delivered). A discount is clawed back in the same proportion, so a coupon is not kept in full on a partial return. An operator may override the amount **downwards only** — that is where a restocking fee goes; upwards would make `orders_write` a way to pay out an arbitrary amount against an order. A running total of every earlier refund on the order is checked too, so three separately-correct partial refunds cannot exceed what was paid.

`return_single_open_per_order` is a partial unique index over the open statuses, not a controller check — two concurrent "return this order" submissions both pass a check-first version, and the second refunds items the first is already refunding. `restocked` is the flag that makes receiving idempotent, read and written inside the same transaction as the increment, exactly as `Order.stockReserved` is for checkout. Restocking is the operator's explicit choice because damaged goods come back and do not go back on the shelf. `Order.paymentStatus` becomes `Refunded` only on a *whole*-order return; a partial one leaves it `Paid`, because it was — marking it otherwise would make every revenue query in `stats.ts` drop the part the customer kept.

The three return emails are transactional and check neither `emailOptOut` nor carry an unsubscribe link, for the same reason a receipt does not: opting out of marketing is not opting out of being told whether your refund happened.

**`status` and `paymentStatus` answer different questions** — "where is the parcel" vs "has the money moved" — and the dashboard filters on each differently (`stats.ts`: `PLACED_ORDER` for counts, `PAID_ORDER` for revenue). Reporting revenue off `status` would count abandoned checkouts; reporting order counts off `paymentStatus` would erase cancelled orders.

**Controller wrapper** — every controller is wrapped in `TryCatch` from `src/middlewares/error.ts`, which forwards rejections to `errorMiddleware`. Errors are thrown as `next(new ErrorHandler(message, statusCode))` (`src/utils/utiliy-class.ts` — note the spelling). Do not add try/catch inside controllers; the wrapper handles it.

**The customer's own account is `/api/v1/address` plus four routes on the user and product routers**, and all of it is `verifyUser`/`requireSelf` — there is no operator path into any of it.

`Address` is the saved shipping book, and it is deliberately **not** referenced by `Order`: the five address columns on an order are a copy taken at checkout, because an order records where it was *actually* sent. A foreign key would let a customer edit the destination of a shipped parcel and would break outright when they delete the address afterwards. One default per user is a partial unique index (`address_single_default`), not a controller check — "clear the old default, then set the new one" is a read-then-write and two concurrent requests both pass the read. Every handler scopes its query by `userId` from `req.appUser` in the same `where` as the row id, so an address id is a filter and never authority; `updateMany`/`deleteMany` are used for exactly that reason.

`PUT /user/:id` (profile) wears `requireSelf`, which is stricter than the `selfOrAdmin` on the GET **on purpose**: `customers_read` is the right escape hatch for looking at a customer record and the wrong one for rewriting it. It reads only `name`/`gender`/`dob`. Email and phone are identity, and the only thing that writes them is `PUT /user/:id/identity`, which takes **nothing from the body** — it calls `providerIdentities()` and asks Firebase what the uid actually has linked. A bearer-uid API that believed a posted email would let anyone who learned a uid write an address onto that account and, because the column is unique, squat on an address someone else is about to sign up with.

`DELETE /user/me` is the customer closing their own account. It **anonymises rather than deletes**, because `Order.userId` references the row and a paid order is a financial record that has to outlive the decision to leave: name replaced, email/phone/photo cleared, `deletedAt` stamped, and wishlist/addresses/reviews deleted outright. `user_email_or_phone` was relaxed to `deletedAt IS NOT NULL OR email IS NOT NULL OR phone IS NOT NULL` so a closed row needs no invented placeholder identifier. Every guard in `middlewares/auth.ts` refuses a row with `deletedAt` set — that check is the *only* thing that makes closure take effect, since Firebase will happily keep authenticating the same uid — and `newUser` refuses to revive one.

**Auth is split by surface, and the split is the design.** The storefront passes the Firebase UID as `?id=<uid>`; **admin routes verify a Firebase ID token** (`Authorization: Bearer …`, `src/utils/firebaseAuth.ts`) and take the caller's uid **from the token, ignoring `?id=` entirely**. Reading both would be worse than either: an operator could authenticate as themselves and then act as somebody else by editing one query parameter.

The reason the console needs tokens is not that a uid is guessable — it is that a uid says nothing about *how* its owner signed in. "Operators must use Google, with a session no older than a day, re-authenticated before changing access" cannot be enforced in the console's UI: an attacker who signs in as the operator on the storefront gets the same uid and calls the admin API directly, never loading a line of console code. `verifyAdminToken` checks `sign_in_provider` against `ADMIN_SIGN_IN_PROVIDERS` (default `google.com`), `auth_time` against `ADMIN_SESSION_MAX_AGE_HOURS` (default 12), `sign_in_second_factor` when `ADMIN_REQUIRE_MFA=true` (default off — enabling it before operators enrol locks everyone out, owner included, and Firebase MFA needs Identity Platform), and passes `checkRevoked` so disabling an account takes effect immediately rather than up to an hour later.

`requireRecentAuth` is step-up: every `/access` mutation needs a sign-in within the last five minutes, answered as `401 {code: "REAUTH_REQUIRED"}` so the console can prompt (`src/admin/stepUp.ts`) instead of failing. A token refreshes itself silently forever, so `auth_time` is the only thing that distinguishes an operator making a decision from a tab left open since Tuesday.

**Unconfigured is fail-closed in production**: with `NODE_ENV=production` and no `FIREBASE_*`, admin routes answer 503. A console silently protected by a string in a URL while the docs, the code and the UI all claim otherwise is worse than one that is plainly broken. In development it falls back to `?id=` so the dev sign-in bypass keeps working — which also means a *real* Google sign-in on the console needs `FIREBASE_*` set in `backend/.env`, and says so in the error.

`User.id` is a `TEXT` column holding the Firebase UID, not a generated key. `Product.id` is likewise `TEXT` and still holds the original 24-char Mongo ObjectId hex for rows that predate the Postgres migration, so historical `OrderItem.productId` references stayed valid; new products get a UUID.

**Admin routes are pinned to the console's origin.** `originAllowed` (`middlewares/auth.ts`, applied by every console guard through `staffPrologue`) refuses any request whose browser `Origin` is not in `ADMIN_URL`. A *missing* Origin is allowed — it is absent on same-origin GETs and on non-browser callers (curl, the seed script, a probe), where there is no browser to lie about it; a present-but-wrong Origin cannot be forged by page script, so it is trustworthy when it is there. With `ADMIN_URL` unset the pin is off entirely and CORS is the only defence. This is what stops a storefront page — or any other site an admin has open — from driving an admin endpoint with a session that is otherwise just a bearer uid on a query string.

The guards all live in `src/middlewares/auth.ts` and each attaches the loaded user *and its staff row* to `req.appUser` / `req.staff` in one query, so controllers never re-query and never see the two at different instants: `verifyUser` (any known uid), `requireConsoleUser` (token verified and origin pinned, but no console access required — `GET /access/me` only), `requireStaff` (has console access, not suspended), `requirePermission(perm)` (the one every admin route wears), `requireRoot` (the owner account), `selfOrAdmin(param)` (the `?id=` caller must match that route param, or hold `customers_read` — used on `GET /user/:id`, which returns email/dob/role), and `requireSelf(param)` (that route param and nothing else, with no staff bypass at all — used on the profile and identity mutations, because editing a customer's own record is not an operator task and a console that can do it is a console that can impersonate). The residual weakness is inherent to the scheme: a uid is a bearer credential, so anyone who learns one can act as that user. Endpoints must therefore never *return* another user's uid to a non-admin.

**`adminOnly` is gone, deliberately, not deprecated.** It answered "may this caller do anything at all in the console" with one boolean, and leaving it importable is how the next admin route ends up all-or-nothing. Admin routes name the permission they need.

**Deny by default is enforced at boot.** `utils/routeAudit.ts` walks the router stack and throws — before `listen` — if any route under `/api/v1` carries neither a guard nor an explicit entry in its `PUBLIC` map with a reason. A stale `PUBLIC` entry whose route no longer exists is also a failure, so an exemption cannot outlive the endpoint it was written for and be silently inherited. `app.ts` mounts from the same `API` array the audit reads, so the two cannot drift. A forgotten guard is the likeliest way this app gets an access-control hole and it is invisible in testing, because the endpoint works; this turns it into a process that will not start.

**Console access is a `StaffMember` row, not `User.role`.** The two answer different questions and are kept apart: `role` is a customer-record column that **nothing decides anything on** — no server-side check reads it, and the storefront no longer reads it either (it renders every account as a customer and links to the console from nowhere). `StaffMember` (userId, `isRoot`, `permissions[]`, `status`, `grantedById`, `grantedAt`, `note`) is the sole authority. Splitting them is what makes access grantable, narrowable, suspendable and revocable without touching the customer record, and what lets every grant remember who made it. `role` is still written in the same transaction as the grant, but only as a record on the customer row; nothing renders off it.

`Permission` is a Prisma enum (`utils/permissions.ts` holds the catalog, the descriptions and the presets). It is an enum and not a free-text table on purpose: a permission only means something if a route checks for it, so one that can be invented at runtime grants nothing and misleads whoever ticked it. `expandPermissions` adds the read half of every write permission — an operator who can advance an order but cannot open one has a console with nothing in it. Presets (Manager/Support/Catalogue/Analyst) only *fill the checkboxes*; what is stored is the resulting list, so editing a preset next year cannot silently change what someone granted last year may do.

**There is exactly one root, and the database says so.** `staff_single_root` is a partial unique index and `staff_root_is_active` a CHECK — a second owner and a suspended owner are both impossible even from psql. Root is **transferred, never granted**: `access_manage` is refused as an ordinary permission (`GRANTABLE_PERMISSIONS` excludes it), which is what closes the escalation path where an operator holding it promotes themselves to everything. `requireRoot` is a column check rather than a permission check for the same reason. Root also cannot act on its own row — self-suspension would lock the store out of its own administration with no way back over HTTP. The outgoing root keeps every operator permission on transfer, because a transfer that costs you the console is one nobody makes.

Bootstrapping is `npm run grant:root -- <userId>` in `backend/` (`node dist/scripts/grant-root.js <userId>` inside the container) — a shell command on purpose. The first owner has no owner to authorize them, and any HTTP endpoint that could mint one could mint one at any time. It is also the recovery path if ownership lands on an account nobody can sign into.

**Access changes are audited inside the transaction**, unlike every other mutation: `recordAuditWithin` takes the transaction client, so a failed audit rolls the grant back. Elsewhere `recordAudit` stays fire-and-forget — a lost line is cheaper than a failed product update — but an unrecorded grant is a person with permissions nobody can account for.

**Deleting a user with console access is refused** (`deleteUser`). `StaffMember` cascades from `User`, so without that check anyone holding `customers_write` could remove a colleague — or the owner — from the Customers page: a privilege boundary crossed sideways through an endpoint that looks unrelated. Revoke first, then delete.

Suspension takes effect on the operator's **next request**, because every guard re-reads the row and there is no token to wait out. That immediacy is a genuine strength of the bearer-uid scheme and is worth keeping even if the app ever moves to ID tokens: verify the token, then still load the staff row.

`GET /api/v1/access/me` is the console's bootstrap call and sits behind `requireConsoleUser`, not `requireStaff` — "you have no console access" and "your access is suspended" are answers it exists to give, and a guard that refuses non-staff cannot give them. `requireConsoleUser` is not `verifyUser`: it still verifies the ID token and still pins the origin, so the caller is fully authenticated and merely authorized for nothing. Using the storefront's `?id=` guard here would let anyone who learned a uid ask what permissions it holds. It returns *effective* permissions, already expanded and already emptied for a suspended operator, so the client never turns a role name into a permission list of its own.

**Two sign-in providers.** Google popup and Firebase phone (SMS + invisible reCAPTCHA), both on `pages/Login.tsx` behind a method switch and both ending in the same `finishLogin`. A phone account has no email and no photo, so `User.email`/`User.photo` are nullable, `User.phone` is a nullable unique E.164 column, and the `user_email_or_phone` CHECK requires at least one identifier. `newUser` takes either; anything rendering `user.email` or `user.photo` needs a fallback. Phone auth needs the provider enabled in the Firebase console and the domain authorized.

**Dev sign-in bypass** — `client/src/utils/devAuth.ts`, enabled by `VITE_DEV_AUTH_BYPASS=true` in `client/.env`. It stores a fixed uid (`dev-customer`/`dev-admin`) in localStorage and lets the normal `?id=` auth take over, so no provider is involved. `App.tsx` checks it before subscribing to Firebase, and `Header`'s logout clears it. Both guards must hold — `import.meta.env.DEV` is literally `false` in a `vite build`, which is what folds the panel out of production bundles; do not swap that test for a runtime-only flag. `npm run seed:dev` in `backend/` creates the two rows, and is the only way `dev-admin` gets `role = admin` since `newUser` never reads `role` from the body.

**Security invariants** — these were added deliberately and are easy to undo by accident:
- Uploaded filenames are built from a mimetype→extension map in `multer.ts`, never from `originalname`, and `assertRealImage` (`src/utils/validate.ts`) checks magic bytes before the row is written. `uploads/` is served from the same origin as the SPA, so a stored `.html`/`.svg` would be XSS. `/uploads` also sets `nosniff` + a `default-src 'none'; sandbox` CSP.
- `errorMiddleware` only echoes messages from `ErrorHandler` instances. Anything else becomes a generic 500 and is logged, so Prisma/SQL internals never reach the client. Throw `new ErrorHandler(msg, code)` — do not `next(rawError)` with a message you want the user to see.
- Request validation goes through `src/utils/validate.ts` (`requireString`/`requireAmount`/`requireInteger`/`requireEmail`/`requireHttpUrl` + the `LIMITS` table). The columns are unbounded `TEXT`; the caps live here.
- Rate limits are in `src/middlewares/rateLimit.ts`: `globalLimiter` app-wide, `sensitiveLimiter` on coupon lookup and PaymentIntent creation, `writeLimiter` on mutations, `adminLimiter` on everything an admin can reach, `suggestLimiter` on the search type-ahead. `globalLimiter` was raised from 300/min to 900 when suggestions landed: a debounced type-ahead fires on roughly every fourth keystroke, so a fast typist browsing normally can generate a couple of hundred requests a minute alone — and because that limiter is app-wide, tripping it would lock them out of the catalogue and their own cart, not just the dropdown. Adding another high-frequency endpoint means checking this ceiling again. `app.set("trust proxy", 1)` is what makes `req.ip` correct behind the nginx container — one hop only. The `/dashboard` router applies `adminLimiter` with `router.use`, so a new endpoint there is limited by default rather than by remembering to; the admin routes scattered across the product/order/user routers list it explicitly.
- **Every admin mutation writes an audit row.** `recordAudit` (`src/utils/audit.ts`) appends to `AdminAuditLog` — actor, action, target, a human summary and the IP — and the console reads it back at `/activity`. Auth is a bearer uid, so nothing else records *who* changed a row. The write is fire-and-forget and swallows its own errors on purpose: an audit failure must never turn a successful product update into a 500. If the trail ever has to be compliance-grade rather than operator-grade, it belongs inside the mutation's transaction instead. The model has no foreign keys, deliberately — the log must outlive the actor or target being deleted, which is the case you most want a record of.
- `newUser` never reads `role` from the body; admins are promoted in the database.

**Caching** — a single in-process `NodeCache` instance (`myCache`, exported from `src/app.ts`, `stdTTL: 3600` / `useClones: false`) fronts most read endpoints, plus the separate bounded `suggestCache` for search terms (see above). Values are stored as JSON strings, so reads are `JSON.parse(myCache.get(key)!)`. Any mutation must call `invalidateCache({ product, order, wishlist, review, admin, userId, orderId, productId })` from `src/utils/features.ts`. Cache keys are conventional strings: `latest-products`, `categories`, `all-products`, `product-${id}`, `related-${id}`, `reviews-${id}`, `all-orders`, `my-orders-${userId}`, `order-${id}`, `wishlist-${userId}`, `admin-stats`, `admin-pie-charts`, `admin-bar-charts`, `admin-line-charts`. When adding a cached endpoint, add its key to `invalidateCache` too — a missed key shows up as stale data, not an error.

`myCache` was `new NodeCache()`, which means `stdTTL: 0` — entries that never expire, removed only by an explicit `invalidateCache`. That is right for `latest-products` and `categories`, a fixed handful of keys. It is a slow leak for the per-user and per-row ones (`my-orders-${userId}`, `wishlist-${userId}`, `order-${id}`, `product-${id}`, `related-${id}`): a customer who browses once leaves entries nothing will ever delete, because invalidation is keyed on writes that will never come for a user who has gone. The TTL is a memory bound, not a correctness mechanism — writes still invalidate immediately and an expired entry costs one query to rebuild. `maxKeys` is deliberately **not** set here, unlike `suggestCache`: `set` throws on a full capped cache and these callers write inline in a request path that would then 500. The key space is bounded by real users and real rows rather than by attacker-supplied search terms, which is the distinction that makes a cap necessary there and a TTL sufficient here.

**Analytics is one endpoint.** `GET /api/v1/dashboard/analytics?range=7d|30d|90d|12m` (`src/controllers/stats.ts`) answers the whole console in one round of queries: KPIs against the preceding window of equal length, a gap-free bucket series, top products and categories by revenue, the fulfilment mix, the checkout funnel, repeat-buyer rate, inventory and recent orders. It replaced `/stats`, `/pie`, `/bar` and `/line`, which answered overlapping questions over hardcoded 6- and 12-month windows and could disagree with each other on the same screen. `GET /dashboard/activity` reads the audit trail. Both are admin-only.

Two filters run through the file and are **not** interchangeable: `PLACED` (`status <> 'PendingPayment'`) is a real order — checkout writes the row before payment, so an unfiltered count is inflated by every abandoned cart, and a cancelled order was still placed. `PAID` (`paymentStatus = 'Paid'`) is revenue. Both attribute by `createdAt`, not `placedAt`, so the series, the KPIs and the breakdowns can never disagree about which bucket an order belongs to.

The bucket series uses `generate_series` LEFT JOINed to orders. That is what puts the zeros in: grouping orders alone drops quiet days, and the chart then draws a straight line across the gap, which reads as steady trade rather than none.

The dashboard endpoints are **not** cached: they run SQL aggregations rather than loading rows and counting in JS, so the cache no longer earns its place there. Measure before adding caching back. Both filters pair a status column with a `createdAt` range in the same `WHERE`, which is what `Order_status_createdAt_idx` and `Order_paymentStatus_createdAt_idx` are for — the single-column indexes let the planner use one leg and check the other by hand.

**Image uploads** — `singleUpload` (multer, field name `photo`) writes to `backend/uploads/` with a UUID filename, and the product's `photo` field stores that relative disk path. `app.use('/uploads', express.static("uploads"))` serves them, and the client builds URLs as `${VITE_SERVER}/${photo}`. `uploadToCloudinary`/`deleteFromCloudinary` exist in `src/utils/features.ts` and Cloudinary is configured at startup, but the product flow still uses local disk storage — both paths are live, so check which one a given controller uses before changing it.

**Coupons live under the *payement* router, not one of their own** — `POST /payement/coupon/new`, `GET /payement/coupon/all`, and `GET|PUT|DELETE /payement/coupon/:id`, all behind `coupons_read`/`coupons_write`, plus `GET /payement/discount?coupon=<code>` which is the storefront's lookup. That last one used to be unauthenticated, which made it an open oracle for guessing codes by brute force; it now wears `verifyUser` **and** `sensitiveLimiter`, and both halves matter — a known uid is cheap to obtain, so the rate limit is what actually costs an attacker something. **A coupon's conditions live in `utils/coupons.ts`, and there is exactly one copy of them.** `Coupon` carries `isActive`, `expiresAt`, `minOrderValue`, `maxRedemptions` and `perUserLimit`; every one is nullable and null means "no limit", so a row created before those columns existed still behaves as an unconditional discount. `assertCouponRedeemable` is the only thing that decides whether a code may be used, and two callers with different authority share it: `applyDiscount` is the cart's **preview** and is told the subtotal by the browser, so its answer is advisory; `calculateOrderAmounts` is **checkout**, derives the subtotal from the product rows inside the transaction, and its answer is what gets charged. Letting those two grow separate copies of the rules is how a customer gets shown "₹500 off" in the cart and charged full price on the next screen.

The preview passes `subtotal: null` when the client did not send one, which *skips* the minimum-order check rather than failing it — a default of zero would silently refuse every minimum-order coupon.

**There is no `redemptionCount` column, deliberately.** Usage is counted from `Order.couponCode` over **paid** orders (`Order_couponCode_paymentStatus_idx` exists for it). A counter would have to be incremented and decremented by the same three racing callers that settle payment — `/payement/verify`, the webhook, and the expiry sweep — which is the bug class `stockReserved` exists to prevent for inventory. Counting paid orders only also means an abandoned checkout cannot burn a redemption, since checkout writes the order before payment.

The residual race is stated rather than hidden: checkout validates before the money lands, so simultaneous checkouts can take a `maxRedemptions: 100` code to 101. Closing it would mean holding a lock on the coupon row across a third-party redirect. Stock is not given that slack because overselling cannot be absorbed; a bounded discount overshoot can.

`couponConditionsFromBody` distinguishes three states per field — absent (leave alone), explicitly `null`/`""` (clear the limit), or a value — because collapsing the last two would make either partial updates or limit removal impossible. The console's page (`src/admin/pages/Coupons.tsx`) is a full editor; it used to only *generate* codes and leave creating them to psql, which is why the CRUD endpoints existed with nothing calling them.

**Route mounting** (`src/app.ts`): `/api/v1/user`, `/api/v1/product`, `/api/v1/order`, `/api/v1/payement` (spelled that way in URL, route file, and controller), `/api/v1/dashboard` (admin console only: `analytics` + `activity`), `/api/v1/access` (`me`, plus root-only staff management), `/api/v1/address` (the customer's own saved addresses: `my`, `new`, `:id`, `:id/default`), `/api/v1/returns` (both sides of a return — see below), `/api/v1/config` (`storefront`, the tax and shipping rules the cart prices with; the third deliberately public route).

`GET /sitemap.xml` and `GET /robots.txt` are mounted **outside** `/api/v1` and are therefore not subject to `routeAudit`. They live on the API rather than as files in `client/public/` because a sitemap has to list the catalogue and the catalogue is a table — a static file would be a snapshot that is wrong the moment a product is added, and nobody notices a stale sitemap. nginx proxies both paths so a crawler fetches them from the storefront's own origin, which is the only place a sitemap's contents are believed. Checkout spans both order and payement routers: `POST /order/checkout` opens it, `GET /order/:id/payment` re-opens the Razorpay handle for an unpaid order (which is what lets `/pay/:orderId` survive a reload), `POST /order/:id/cancel` cancels and refunds, and `POST /payement/{verify,webhook}` settle it. `/payement/webhook` is the one deliberately unauthenticated route in the app — Razorpay has no uid to send, so it is authenticated by HMAC instead. Wishlist endpoints live under the *product* router: `/api/v1/product/wishlist/{my,:id,delete/:id}`, as do reviews: `/api/v1/product/:id/reviews` (GET public, POST/DELETE need a uid) and `/api/v1/product/:id/reviews/mine`. `GET /api/v1/product/reviews/mine` — every review the caller has written, for the account page — is registered **above** `/:id/reviews` in `routes/product.ts`, because both are two-segment paths and the parameterised one would otherwise match first with `id="reviews"`.

**`backend/dist/` and `backend/src/generated/` are not in git**, and neither is `client/dist/`. `dist` used to be committed and went stale whenever `npm run build` was not rerun — a compiled tree in version control is a second copy of the source that no tooling keeps in step, and every `npm run build` produced a diff nobody read. The Dockerfile builds both in the image, and CI builds them on every push, so nothing depended on the committed copy being current. `npm run build` still writes them locally; they are simply ignored.

## Client architecture

`client/` holds **two applications**, and they share source but not a bundle:

| | storefront | admin console |
|---|---|---|
| entry | `index.html` → `src/main.tsx` → `src/App.tsx` | `admin.html` → `src/admin/main.tsx` → `src/admin/AdminApp.tsx` |
| pages | `src/pages/` | `src/admin/pages/` |
| store | `src/redux/store.ts` (6 API slices + cart + user) | `src/admin/store.ts` (one `adminAPI` slice + `session`) |
| styles | `src/styles/app.scss` | `src/styles/admin.scss` (standalone; imports no storefront partial) |
| firebase | `src/firebase.ts` (auth **+ analytics**) | `src/admin/firebase.ts` (auth only) |
| host | the domain | `app.admin.<domain>` |

They share `src/types/`, `src/utils/` and the Firebase credentials, and nothing else. The storefront's API slices no longer carry admin endpoints at all — product create/update/delete, the unpaginated catalogue, `order/all`, order advance/delete and `user/all`/delete moved to `src/admin/api.ts` — so a shopper's bundle does not contain them. `src/admin/firebase.ts` exists because `src/firebase.ts` calls `getAnalytics()` at import time, and an operator's clicks through customer records are not product analytics.

`src/admin/session.ts` has **five** states, not two: `loading`, `anonymous`, `forbidden` (signed in, no console access), `suspended` (had access, it is paused), and `authenticated`. Each needs a different sentence — a valid customer who is not staff has already signed in, so bouncing them back to the sign-in form would change nothing, and telling a suspended operator they have "no access" sends them chasing a sign-in problem that isn't one. `RequireAdmin` says which. That guard is a courtesy to the operator, never a security boundary; every endpoint re-checks server-side.

**No console request sends `?id=`.** `src/admin/api.ts` attaches the ID token in `prepareHeaders` and retries once on a stale one; the uid is not a parameter of any admin endpoint, which is why none of the hooks takes an `adminId` argument. The dev bypass is the one exception and appends `?id=` itself, because it has no Firebase session to tokenise.

The session also carries `permissions` and `isRoot`, both **computed by the server** and loaded in one call to `GET /access/me` (`src/admin/auth.ts`). The console never expands a role name into permissions of its own — that is how the two sides end up disagreeing about what someone may do, with the client's answer being the one people see.

**One nav list drives the sidebar, the router and the landing redirect.** `src/admin/navigation.ts` gives every section its required permission (or `root: true`); `visibleNav` filters the sidebar, `RequirePermission` gates each route, and `landingFor` picks where `/` goes. A section therefore cannot be visible but unreachable, or reachable but invisible. The overview needs `analytics_read`, so `/` resolves to the first section the operator can actually see — an order-desk account should not meet a refusal every time it signs in. Individual actions are gated with `useCan()` (the "New product" button, order advance/delete, customer delete, the cross-links on the overview): a button that always fails is worse than no button.

`src/admin/pages/Access.tsx` is root's page. Granting takes a **uid picked from a search result**, never a typed email — typing an address into a grant form is how access ends up on the wrong lookalike account, and nothing about that failure is visible afterwards. The console signs itself out after 30 minutes idle (`AdminApp.tsx`), which is defence in depth for an unattended warehouse machine and explicitly *not* a substitute for suspension.

**The account area is one shell over the existing URLs.** `src/pages/account/AccountLayout.tsx` is a *pathless* layout route in `App.tsx` wrapping `/profile`, `/orders`, `/orders/:id`, `/returns`, `/wishlist`, `/addresses`, `/reviews` and `/settings`. The sections deliberately did **not** move under an `/account` prefix: the header, the footer, the order table and the checkout success page all link to `/orders` and `/wishlist` already, and a redirect chain is a worse answer than not moving. `/account` itself redirects to `/profile` because it is what people type. `src/pages/account/navigation.ts` is the one list that says which sections exist — it drives the sidebar *and* the overview's shortcut cards, so a section cannot be visible but unreachable, the same arrangement `src/admin/navigation.ts` has. Checkout (`/shipping`, `/pay/:orderId`) is outside the shell: a sidebar of other places to go is the last thing a payment flow needs. Pages rendered in the shell must not carry the `.page` class themselves, or the padding doubles.

`Settings.tsx` holds three things of increasing weight: the profile form, sign-in-method linking (`linkWithPopup` / `linkWithPhoneNumber`, then `PUT /user/:id/identity`, which tells the server nothing about what was linked), and closing the account. Closing signs the local session out immediately — the uid stops being accepted the moment the server stamps `deletedAt`, so a UI that still believed it was signed in would 401 on every subsequent request.

**"Buy these again" re-fetches, it does not replay.** An order's items are a snapshot carrying *the price that was paid*, so pushing them into the cart as they stand would show last year's price while checkout re-derives the real one server-side — a total the customer never agreed to. `OrderDetails.tsx` dispatches `productAPI.endpoints.ProdectDetails.initiate` per item instead, which is also the only way to learn current stock; anything discontinued or sold out is named in a toast rather than silently dropped. The invoice is real markup hidden on screen and revealed by the `@media print` block in `account.scss`, which hides everything else — "save as PDF" is then a device the customer already has, and there is no generator to keep in step with the page.

**Checkout prefills from the address book.** `Shipping.tsx` reads `useMyAddressesQuery` and starts on the default instead of five blank fields. The prefill is applied *during render* guarded by a `prefilledFor` id, not in an effect — an effect paints the empty form first and then replaces it. Editing any field flips the selection back to "new address", because an edited prefill is a different address and leaving it attached to the saved row would mean the picker claims one thing while the order ships to another. Saving the typed address is best-effort and never blocks the checkout: the customer asked to buy something, not to manage their address book.

**There is a 404, and there are policy pages.** `App.tsx` ends in a `path="*"` catch-all rendering `pages/NotFound.tsx`; before it, an unknown path rendered the header and footer with nothing between them, which reads as a page that failed to load rather than one that does not exist. `pages/static/documents.ts` holds four policy documents (shipping, returns, privacy, terms) plus an About as structured data, rendered by one `StaticPage` component — six instances of the same thing differing only in words. Contact is its own component because it is actionable details rather than prose, and there is deliberately no contact *form*: a form with nowhere for the messages to land is worse than an address that works.

Each slug is its own route rather than one `/:slug` catch-all, which would swallow every unknown path and render a blank policy page where a 404 belongs. The routes are `/shipping-policy` and `/returns-policy`, **not** `/shipping` and `/returns` — those are the checkout address step and the customer's own returns list.

**The policies are complete templates with visible `[bracketed]` placeholders, not finished legal text.** Anything the code cannot know — the registered entity, the postal address, the governing jurisdiction — is a bracket rather than a plausible invention, because a returns policy stating a made-up address is not a draft, it is parcels posted somewhere that does not exist. Have a lawyer read them before launch.

**Per-page metadata is `components/Seo.tsx`**, four `document` writes and a cleanup rather than `react-helmet` — the storefront's critical path is measured in kilobytes and a dependency would cost more than the feature. `index.html` carries one static title and description, which is all *every* page had before: a product page, the cart and the returns policy all shared "shop fashion, tech and beauty", and every link anyone pasted anywhere previewed as the home page. It does not make the SPA crawlable on its own — a crawler that does not run JavaScript still sees the shell — it makes the pages correct for the crawlers that do and for every link preview, which is the part users see. `/search` and the account pages pass `noIndex`: every filter combination is its own URL, and letting a crawler enumerate them fills an index with near-duplicates competing with the product pages that should rank. `Seo` also drops the query string from the canonical, for the same reason.

**The cart keys its lines on productId *and* variantId.** Two sizes of one shirt are two lines; keying on productId alone meant adding the medium after the small silently *replaced* it, and the customer received one shirt having chosen two. `removeCartItem` therefore takes the line identity rather than a product id, and the list is keyed on it rather than on the array index — an index key makes React reuse the wrong row's DOM when one is removed.

**The cart prices from the server's rules, not from literals.** `useStorefrontConfig` (called once from `App`, not from the cart — the totals appear in the header badge and on the product page too) loads `GET /config/storefront` into the cart slice, and `calculatePrice` reads it. The slice starts with the old hardcoded defaults, so an unreachable config endpoint degrades to exactly the behaviour the app had before it existed. The preview is advisory regardless: checkout re-derives every figure server-side and that answer is what gets charged. The delivery threshold and return window are now read from the same place on the home page, the product page and the cart, instead of being four copies of `₹1,000` and `7 days`.

**The variant picker marks unreachable values, and that distinction is load-bearing.** `components/VariantPicker.tsx` disables (with a strikethrough) values that no variant offers *given the other selections* — a shirt in blue in every size but red only in medium leaves most of the grid empty, and a picker that offers everything sends people to combinations that were never made with no explanation. Sold-out combinations stay **selectable**: a customer has to be able to land on one to be told it is sold out and offered a back-in-stock alert. Unreachable and sold-out are different states and must not look the same. Choosing a value clears any other selection it strands, so the customer is one click from a real variant rather than in a state with no Add to cart and nothing indicating which choice to change.

Nothing is preselected. Preselecting means someone who never opened the picker still buys *something*, and the size they receive is whichever happened to be first in the admin form.

**"Buy these again" resolves the variant too.** It already re-fetched each product rather than replaying the snapshot (the order carries the price that was paid, and pushing that into the cart shows a total checkout would not honour); it now also looks the variant up in the current catalogue and names anything discontinued rather than silently adding the product without one — which would put the cheapest size in the cart under the name of the one they bought.

**The console has a returns queue** (`src/admin/pages/Returns.tsx`): cards rather than a table, each carrying only the actions its current status permits. Reading needs `orders_read` and every action needs `orders_write`, gated with `useCan` — an operator who can only read gets a queue they can watch and a support answer they can give. The dispatch form lives on the order page rather than in a separate "add tracking" screen, for the reason above.

**State** — `src/redux/store.ts` composes six RTK Query API slices (`userAPI`, `productAPI`, `orderAPI`, `wishlistAPI`, `addressAPI`, `returnsAPI` — which also serves `/config/storefront`, since that is not about products) plus two plain slices (`userReducer`, `cartReducer`). Each API slice sets its own `baseUrl` from `VITE_SERVER` and manages cache invalidation through `tagTypes` / `providesTags` / `invalidatesTags`. Adding a slice means registering both its reducer and its middleware in `store.ts`.

Storefront mutations take the user id as a query param (`?id=${userId}`) to satisfy `verifyUser`/`requireSelf` — follow that pattern when adding **storefront** endpoints. It does not apply to the console, which sends an ID token and never `?id=` (see `src/admin/api.ts`).

**Keep the storefront's critical path small.** What a shopper downloads before anything renders is ~138 kB gzipped across 13 files. That figure came from walking the *static* import graph out of `dist/index.html` — lazily imported chunks are excluded, so it is not the same number as `du` over `dist/assets`. No script for this is committed; re-measure the same way rather than trusting a total from the build log. Four things were removed from that path and should not come back:

- **`moment` is not a dependency.** It was 19 kB gzipped in a chunk every page loaded, pulled in by one dead `getLastMonths()` in `utils/features.ts` left over from the admin charts. `features.ts` also exports `formatINR` and `orderStatusClass`, which most pages use, so anything heavy imported there lands in shared code — check what a new import costs before adding one to that file.
- **Firebase Analytics is loaded at idle, not at import.** `src/firebase.ts` is imported by `App.tsx` for `auth`, so a module-scope `getAnalytics(app)` meant nothing rendered until the measurement SDK had downloaded and parsed. It now dynamic-imports behind `requestIdleCallback`, guarded by `isSupported()` — which is not optional, because `getAnalytics` *throws* where cookies or IndexedDB are unavailable (private windows, some webviews) and at module scope that took the whole app down with it.
- **The Firebase *auth* SDK is dynamically imported too** (~21 kB gzipped, plus ~9 kB for `firebase/app`). Nothing that renders on a first paint may `import ... from "./firebase"` at module scope. Two things did: `App.tsx`, and `Header.tsx` for its one `signOut` call — and Header is on every page, so that alone pinned the SDK to the entry chunk for the sake of a handler most visitors never trigger. Both now import it inside the function that needs it (`hooks/useAuthBootstrap.ts`, `logoutHandler`). A shopper who never signs in never downloads it.
- **`WishList` was statically imported by `App.tsx`** while every other page was lazy, so its chunk shipped to everyone. Every route now comes from `routes/lazyRoutes.ts`; add new ones there rather than with a bare `lazy(...)` in `App.tsx`, or they lose prefetching as well.

**Auth flow** — `hooks/useAuthBootstrap.ts` subscribes to Firebase `onAuthStateChanged`, fetches the app user via the plain-axios `getUser(uid)` helper in `redux/api/userAPI.ts` (not an RTK Query endpoint, because it runs outside React), and dispatches `userExits`/`userNotExits`.

**The app does not wait for it.** `App.tsx` used to render `loading ? <Loader/> : <Router/>`, so the catalogue, the cart, every product page and the policy documents all sat behind a Firebase round trip they have no use for — and when Firebase could not be reached, the whole shop sat on a spinner for ever with no way out but a reload. Only a guarded route actually needs the answer, so `ProtectedRoute` takes `loading` and waits there instead. Do not reintroduce a global gate on `loading`; if a new component needs the user, it must tolerate `null` while the session resolves.

The hook loads Firebase eagerly when a stored session is detected and at idle otherwise. That peek at `localStorage` decides *when*, never *whether* — the SDK always loads and always answers, because inferring "signed out" from a storage key would sign out anyone whose key format the peek did not recognise.

**Routes are prefetched on intent, and that is what makes a click feel instant.** Code splitting moves the cost of a route from the bundle to the click: the first navigation downloads its chunk while the visitor watches a spinner. `routes/lazyRoutes.ts` declares every lazy route once and exports `prefetchRoute(path)` / `prefetchProps(path)`; the header links, the account menu and the product cards spread those onto themselves so a hover, focus or touch starts the download tens to hundreds of milliseconds before the click commits. `import()` is idempotent — the module registry caches the promise — so prefetching something already loaded costs nothing and needs no bookkeeping.

Product cards warm **both halves** of what the click needs: the route chunk and, through RTK Query's `usePrefetch("ProdectDetails", { ifOlderThan: 60 })`, the product's own data. `ifOlderThan` is what stops a pointer swept across a grid from firing a request per card.

**Cache lifetimes on catalogue reads are explicit, not defaulted.** RTK Query drops an unused entry after 60 seconds, so home → product → back re-fetched a list the *server* was answering from memory anyway — a round trip whose only effect was a spinner. `latestProducts`, `seatchProducts`, `ProdectDetails` and `relatedProducts` keep data for 300s and `categories` for 3600s. This governs how long **unused** data survives, not how stale it may get: every one of them carries `providesTags: ["product"]`, so an operator's edit still invalidates them at once.

`ProtectedRoute` gates routes on `isAuthenticated` and `adminOnly`/`admin`. A signed-out visitor is sent to `/login` with `state.from` set to where they were headed, and `Login` redirects back there once a user exists — so `/login` must **not** itself be wrapped in `ProtectedRoute` (that loops). A signed-in non-admin hitting an `adminOnly` route still goes to `/`.

Login is only ever demanded in four places, and each explains itself: checkout, adding to a wishlist, writing a review, and the account pages (everything under the `AccountLayout` shell — `/profile`, `/orders`, `/returns`, `/wishlist`, `/addresses`, `/reviews`, `/settings`). Browsing, searching, the cart and reading reviews are all open — don't add a gate elsewhere without a reason.

**Every route to `/login` carries where to come back to, and `utils/loginRedirect.ts` is the only thing that builds it.** `ProtectedRoute` used to be the sole caller that set `state.from`; the header's sign-in icon, "Log in to checkout", "Buy now" and the review prompt all dropped it, so signing in from any of them landed on the home page and the customer had to find their way back and click the same control again. A gated action that answers a click with a toast and no route (`toast.error("Please login…")`) is a dead end rather than a gate — send them to `/login` with `loginState(currentPath(location))` instead. Checkout entry points deliberately pass `"/shipping"` rather than the current page: they asked to buy something, and sign-in was the only thing in the way.

`safeReturnTo` sanitises on the way in *and* on the way out, because the value is handed to `<Navigate to={from}>` — `//host` is a different site and `/login` is the redirect loop that makes `/login` unsafe to wrap in `ProtectedRoute`. It is a pure function and is unit-tested; history entries outlive a build, so `readLoginState` re-checks what it finds.

**Signing out goes home, explicitly.** `Header`'s `logoutHandler` calls `navigate("/", { replace: true })`, matching `Settings.tsx`'s account closure. Without it, signing out from an account page fires `userNotExits`, `ProtectedRoute` re-evaluates, and the customer who just asked to leave is shown the *sign-in form* with `state.from` pointing back at the page they left. `replace` so the back button cannot return to a page the session no longer permits.

`components/LoginIntent.tsx` finishes the one action worth resuming across sign-in — the wishlist heart, which is otherwise still a click away from where the customer left it. The intent rides in the same router state and is cleared before the mutation fires, so a reload cannot replay it. It is deliberately not a general pending-action queue and not storage-backed: router state is discarded by the next navigation, which is exactly the lifetime this should have.

**Checkout pages** are `/cart` → `/shipping` → `/pay/:orderId`. `Shipping` calls `POST /order/checkout` and navigates to the returned order id; `Checkout.tsx` (the pay page) fetches its own Razorpay handle from that id and opens the modal via `utils/razorpay.ts`, which injects `checkout.razorpay.com/v1/checkout.js` on demand. The order id being in the **path** is deliberate — the old page carried a one-shot Stripe `clientSecret` in router state and minted a new PaymentIntent on every refresh. Nothing on this page can lose a payment: if `verifyPayment` fails the customer is told to wait, never to pay again, because the webhook settles the order regardless. `resetCart` runs on payment success, not at checkout creation, so an abandoned payment leaves the cart intact.

**Cart totals** are computed client-side in `cartReducer.calculatePrice`: 18% tax, ₹200 shipping waived above ₹1000 subtotal, minus coupon discount. Currency is INR throughout, including the Razorpay order — render money through `formatINR` in `src/utils/features.ts` rather than hand-writing a symbol, which is how several screens ended up showing `$`.

**Product content** — a product carries `name`, `photo` (hero image), `description`, `price`, `stock`, `category`, `brand`, plus `ProductImage` rows for gallery shots, `ProductSpec` rows and `Review` rows. `highlights`, `inTheBox` and `warranty` are newline-separated **text columns**, not tables — they are only ever written and read whole; the serializer splits the first two into arrays so no component knows how they are stored. `ProductSpec` is free `group`/`label`/`value` rows rather than fixed columns, because a laptop and a torch share almost no attributes; the page groups them into sections in saved order and folds category/stock/item-code/listed in as "General". Specs arrive from the admin form as a **JSON string** (the body is multipart, carrying images), parsed by `parseSpecs` in `utils/validate.ts`, and submitting them replaces the whole set. `serializeProduct` flattens the gallery into `images: string[]` with the hero at index 0, and attaches `ratings`/`numOfReviews`, which are **derived** from the Review table by `utils/reviewStats.ts` — not columns, and 0 when nothing has been reviewed. Only `getSingleProduct` includes the gallery; list endpoints emit `images: [photo]` because cards only need the hero.

`ProductImage` (`client/src/components/ProductImage.tsx`) handles rows whose upload file has gone missing; use it rather than a bare `<img>` for product photos.

**Reviews** — `Review` is unique on `(productId, userId)`, so posting twice edits rather than duplicates, and `newReview` upserts instead of check-then-insert. Rating is 1-5 by CHECK constraint. Any signed-in user may review; the "Verified purchase" badge is derived from that user's order history, never from the request. Writing a review must invalidate the product too (`{ product: true, review: true, productId }`) because the average rating is baked into every cached product payload.

Product create/edit uses `productUpload` (multer `.fields()`: one `photo` + up to four `photos`), not `singleUpload`. Uploading gallery files **replaces** the existing gallery and deletes the old files.

**Search routing** — `/search` browses everything and reads `?q=` and `?category=`; `/search/:id` is the older "term in the path" form and still resolves to the same page. Category links anywhere in the app should use `/search?category=<name>`.

**The header search box is a combobox, not an input** (`components/SearchBox.tsx`). Recent searches, product matches and category matches share one **flat** item list so the highlighted row is a single index — keyboard navigation across three separate sections otherwise becomes a (section, index) pair and every handler has to know the section boundaries. Selecting a product navigates to `/product/:id` directly; skipping the results page is the entire point of a type-ahead. The ARIA attributes (`role="combobox"`, `aria-activedescendant`, `role="option"`) are load-bearing: without them a screen reader announces nothing as the arrows move. Rows use `onPointerDown` with `preventDefault`, not `onClick`, because click fires after blur and the blur would have already closed the panel.

Suggestions cost four layers of not-asking, cheapest first, and each one exists because the layer behind it is more expensive: terms under 2 characters never fire (an empty box shows `utils/recentSearches.ts` from localStorage — zero requests); `hooks/useDebounced.ts` collapses a burst of keystrokes into one request per pause; RTK Query caches per term with `keepUnusedDataFor: 300`, so backspacing through a word is free; and the server caches in `utils/suggestCache.ts`.

That cache is **deliberately not `myCache`**. Its key is the user's search term, so the key space is unbounded and attacker-controlled — on the shared instance a script issuing `?q=aaa`, `?q=aab`, … would evict every product and order on its way to exhausting memory. It is a separate NodeCache with `maxKeys: 500` and a 60s TTL, and `rememberSuggestion` swallows the throw that `set` raises when full, because a full cache must not turn a search into a 500. `invalidateCache({ product: true })` calls `flushAll()` on it — there is no set of keys to name, since any term might have matched the product that changed.

**Console tables** go through `src/admin/components/DataTable.tsx`, which is hand-rolled rather than `react-table`: it splits a column's sortable/searchable `value` from what it `render`s. The old admin tables stored a `<Link>` element *in the data*, so they could only sort rows by the identity of a React element — which is why none of them sorted usefully — and had no search at all.

The storefront has its own `components/DataTable.tsx` with the same `value`/`render` split, page size 6, no search. It is a near-twin of the console's and deliberately **not** an import of it: the two apps share types and utils and nothing else, and the console's table is styled with `c-` classes from `admin.scss`, which the storefront never loads — sharing it would mean shipping console CSS to shoppers or parameterising every class name.

Both replaced `react-table` v7, which is gone from the project along with `src/types/react-table-config.d.ts` (the module augmentation its plugin typings needed). It cost 18 kB gzipped on the `/orders` route to render six rows. Sorting the *value* rather than the rendered cell also fixed Amount and Discount, which were pre-formatted strings and so sorted lexically — `₹1,000` below `₹900`.

**Console charts.** One chart component, `src/admin/components/TrendChart.tsx` (chart.js, single series, area under a 2px line, points only on hover). It is single-series by design: revenue and order count are orders of magnitude apart, and drawing them together needs a second y-axis — the chart that most reliably invents correlations that aren't there — so the pages give the reader a toggle and redraw one series at a time. Ranked top-N data uses `BarList` (plain HTML rows with the name and value as full-size text, the bar as secondary encoding) rather than a horizontal bar chart, which would spend its width on an axis nobody reads and truncate the labels. The status colours in `Analytics.tsx` are ordered so green and red are never adjacent — that pair is the classic colour-vision failure — and every row carries its label and count as text.

**Styles** are SCSS partials under `src/styles/`, aggregated by `app.scss` — the only stylesheet `main.tsx` imports. They use the **Sass module system** (`@use`), not `@import`, which Dart Sass 3 removes. Each partial declares its own dependencies at the top, conventionally:

```scss
@use "tokens" as *;   // colours, spacing, radii, breakpoints, `upto()`
@use "mixins" as *;   // flex/grid/square/btn helpers
@use "base" as *;     // %btn-base, control/select-caret/range-input
```

(`_mixins.scss` was `admin-styles/_mixin.scss`; it was never admin-specific — thirteen storefront partials use it — and `admin-styles/` is gone.)

`as *` keeps members unqualified (`$ink-700`, `@include flex(...)`) rather than namespaced. A new partial needs its own `@use` header *and* a `@use` line in `app.scss`; the order in `app.scss` still sets the cascade, because a module's CSS is emitted where it is first loaded (a module loaded twice is only emitted once). `_tokens` also carries the legacy `$primary-color`/`$second-color` aliases the admin partials read.

Prefer a mixin over `@extend` for anything shared across files — `@extend` of a plain class does not cross module boundaries, which is why the card grid is the `product-grid` mixin. The `%btn-base` placeholder is extended across modules and does work.

`admin.scss` shares none of this. It carries its own tokens and its own `l-`/`c-`/`is-` naming, so no storefront style change can reach the console by accident, and the console's neutral blue is visibly not the shop's rose — an operator can always tell which app they are in.

Colours belong in `_tokens.scss`, not inline in a partial. Form controls go through the `control` / `select-caret` / `range-input` mixins in `_base.scss` so focus rings stay consistent — the theme is dark, and a stock light control is glaringly out of place. Google Fonts are linked from `index.html`, not `@import`ed in SCSS: a CSS `@import` that follows any rule is ignored by the browser, which is what used to happen.

Routes are lazy-loaded in both apps. `App.tsx` has **no** admin routes any more — nothing an admin can do is reachable from the storefront origin. The one `/admin/*` entry left is a `<Navigate to="/" replace />` catch-all, kept so the old bookmarks land somewhere sane; it renders nothing and must not grow a child route. Everything else falls through to the `path="*"` 404 below it.

## Conventions worth matching

- Shared response/request types live in `client/src/types/api-types.ts` and `client/src/types/types.ts`; backend request-body and query types live in `backend/src/types/types.ts`. They are duplicated by hand, not generated — update both sides when an endpoint's shape changes.
- Product `category` is lowercased on write (`category.toLocaleLowerCase()`), so queries should assume lowercase.
- Several existing identifiers are misspelled and are load-bearing (`payement`, `utiliy-class`, `useSeatchProductsQuery`, `ProdectDetails`, `userExits`). Match the existing spelling rather than "fixing" it in passing.
- The API emits `_id` (and `id`) on every entity purely for client compatibility. Add it via `src/utils/serialize.ts` rather than hand-rolling the mapping in a controller.
- `scripts/migrate-mongo-to-postgres.ts` is the one-shot Mongo→Postgres ETL, kept as the record of how the data was transformed. It imports `mongoose`, which is no longer a dependency — running it again needs `npm i mongoose --no-save` first.
